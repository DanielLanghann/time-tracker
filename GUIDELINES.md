# Guidelines

Rules for everyone working on this repository, humans and coding agents alike.

- **MUST / NEVER** are hard rules. If a task seems to require breaking one, stop and raise it instead of working around it.
- **PREFER** marks the default. Deviate only with a reason stated in the PR or commit message.

## Project at a glance

- **Backend:** Django + Django REST Framework in `services/api`, managed with uv
- **Frontend:** Vue in `services/frontend`
- **Database:** PostgreSQL
- **Domain apps** live in `services/api/apps/`. Dependencies point in one direction only:

  `reports` → `tracking` → `customers` → `workspaces` → `accounts`

## Architecture

- An app MUST only import from apps to its right in the dependency line above. Needing to import "upwards" means the code belongs in a different app.
- Views MUST stay thin: parse the request, call a service or selector, return the response.
- Writes go in `services.py`, reads in `selectors.py`. Business rules (one running timer per user, an item belongs to its entry's stream, rate resolution) live in services, NEVER in views or serializers.
- Roles and hourly rates belong to `Membership` and `StreamMembership`, NEVER to `User`.
- All access to workspace-owned data MUST go through the central workspace scoping. NEVER use `Model.objects.all()` in API code.

## Code quality and delivery

- Every change MUST come with tests (pytest-django). Bug fixes start with a failing test that reproduces the bug.
- Code MUST pass `ruff check` and `ruff format`.
- CI runs on every push: ruff, pytest, `makemigrations --check` and `manage.py check --deploy` against production settings.
- One Docker image for all environments, served by gunicorn in production.
- NEVER edit or delete a migration that has been merged to `main`. Create a new migration instead.
- Configuration MUST come from environment variables. NEVER commit secrets or `.env` files. `.env.example` MUST list every variable the app reads.
- NEVER add new dependencies or infrastructure components unless the task explicitly asks for them.

## Data correctness

Time and money are what this application is about. Mistakes here end up on customer invoices.

- `USE_TZ = True`. Store all timestamps in UTC. Convert to the user's time zone only for display and for deciding which day an entry belongs to.
- Code that handles days, weeks or durations MUST have tests covering daylight saving time transitions.
- Money and rates MUST use `Decimal`, NEVER `float`.
- The resolved hourly rate is stored on `TimeEntry` when it is saved. NEVER recalculate amounts of existing entries from current rates.
- Core models have `created_at`, `updated_at` and `created_by`.
- Archive instead of delete. Foreign keys pointing to booked time use `on_delete=PROTECT`.

## API contract

- The OpenAPI schema generated by drf-spectacular is the single source of truth for the API.
- The frontend uses a TypeScript client generated from that schema. NEVER hand-write API types in the frontend.
- All endpoints live under `/api/v1/`. Breaking changes require a new version.

## Security

- Containers MUST NOT run as root. Application code is owned by root and only readable for the app user. Services listen on ports ≥ 1024.
- Production containers run with `read_only: true`, `cap_drop: [ALL]` and `no-new-privileges:true`.
- HTTPS only, secure cookies, CSRF protection, rate-limited login.
- Every workspace-owned endpoint MUST have a test proving that one workspace cannot read or modify another workspace's data.
- Time entries are personal data. Visibility rules (own entries, stream members, admins) MUST be decided and documented before the first endpoint that exposes other users' entries, and every such endpoint MUST have permission tests.

## Logging and privacy

- NEVER log, at any level: passwords, tokens, session IDs, API keys, cookies.
- Personal data (names, email addresses, time entry descriptions) MAY only be logged at DEBUG level.
- DEBUG logging and `DEBUG=True` MUST NOT be enabled in production. A startup check enforces this.
- At INFO and above, log IDs only, for example `user_id=42 entry_id=1337`.
- NEVER log request bodies, headers or whole model objects. `__str__` usually contains personal data, so f-strings like `f"{user}"` or `f"{entry}"` count as logging personal data.
- Authentication views use `@sensitive_post_parameters()`. Error tracking runs with `send_default_pii=False`.

## Operations

- Automated Postgres backups, with a restore tested regularly. This data drives customer billing.
- Error tracking (Sentry or self-hosted GlitchTip), structured logs and a `/health` endpoint.
- Dependency updates via Dependabot or Renovate.

## Deferred on purpose

Do NOT build any of the following unless a task explicitly asks for it:

Kubernetes, Celery and background jobs, caching, invoicing, approvals, mobile apps, and anything for a hosted version (signup, billing, multi-tenant onboarding).

The architecture leaves room for all of them. None of them block internal use.

## Before finishing a task

Run from `services/api` and make sure everything passes:

```bash
uv run ruff check .
uv run ruff format --check .
uv run pytest
uv run python manage.py makemigrations --check --dry-run
```

Coding agents MUST run these before reporting a task as done, and MUST report any command that fails instead of skipping it.
